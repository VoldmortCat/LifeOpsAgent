## 你的原始需求与核心痛点

1. **提示词膨胀与耦合**  
   每增加一个功能就要写一大段提示词，里面混杂角色设定、业务规则、异常处理。多 Agent 联调时，调用逻辑和调度规则全部硬塞在提示词和工具描述里，牵一发而动全身。

2. **Agent 不能当“懂业务的中枢”**  
   LLM 本质上只是基于概率的模式匹配，并不真正理解业务。让它自己琢磨怎么调度、怎么降级，结果不可靠，也把控制权交给了黑盒。

3. **复用与精简配置的矛盾**  
   你承认不同业务需求必然需要不同的逻辑链路，但希望不要每次都从零堆砌，追求用极少的配置做出适配，避免大量定制代码和巨型提示词。

4. **具体场景：行程助手调账单助手**  
   travel-agent 需要 bill-agent 提供用户经济数据，但数据可能不全，这时候该怎么降级处理？你不希望这个降级逻辑变成一大坨常驻在 bill-agent 里的固定提示词，也不希望完全靠外部工作流把 bill-agent 变成无脑工具而丧失内聚性。

---

## 最终更新后的解决方案

你的方案可以用一句话概括：

**把降级策略作为“休眠资产”预置在 bill-agent 内部，由外部传入的状态标识按需激活，平时这些降级提示词完全不参与上下文，保持 Agent 日常运行的精简与干净。**

### 核心机制

1. **bill-agent 内部预置降级策略库**  
   所有可能的降级处理方式（“数据不全时用近两月日均估算并加免责声明”、“完全无数据时直接告知无法分析”、“部分类目缺失时如实说明缺失项”等）都写好，以条件块的形式存在 bill-agent 的配置里，但默认不加载。

2. **用状态标识作为“激活开关”**  
   travel-agent（或上游编排层）在调用 bill-agent 时，除了传递自然语言指令外，还附带一个明确的状态标识，如 `data_status: "degraded"` 或 `"no_data"`。这个标识不是让 bill-agent 自己去琢磨，而是直接告诉它：“现在请激活第 X 号应急手册”。

3. **按需注入，动态拼装 prompt**  
   当 bill-agent 收到请求时，系统根据标识从策略库中取出对应的降级指导提示词块，注入到本次调用的 system prompt 中。请求处理完毕后，这部分降级提示词就消失了，下次普通调用依然是精简的日常 prompt。

4. **bill-agent 依然是执行者，不做决策**  
   它在降级模式下，只是严格遵循被激活的那套指引来组织回答——该怎么说局限性、该用哪种替代数据、该在什么情况下直接拒绝生成分析，全都写在策略块里，不需要它自己临场判断。

### 日常运行 vs. 降级激活的对比

- **日常调用（无标识）**  
  bill-agent 只带着通用角色设定和基本操作规范，像一个只带着日常工具包的员工，轻装上阵。

- **降级调用（带标识）**  
  bill-agent 在本次任务中额外获得一份“应急处理指南”，知道自己当前处于数据异常状态，该走哪条既定的处理路径。处理完这一次后，指南自动归档，下次又从干净状态开始。

### 这个方案的独到之处

你之前接触过“外部编排”和“状态机”的思路，但最终还是选择了把降级策略内置、用标识激活的方式。这本质上是在**内聚性和简洁性之间找到了一个非常务实的平衡点**：

- 比纯外部编排更内聚：bill-agent 不需要依赖外部链来拼完整 prompt，降级知识和表达逻辑都在它自己的配置范围内。
- 比写死长 prompt 更经济：没用的策略不占上下文，节省 token，也避免 LLM 被无关信息干扰。
- 比让 LLM 自主决策更可控：激活哪个策略由外部的确定性标识决定，LLM 只照着激活后的指令执行，不参与“该不该降级”的判断。
