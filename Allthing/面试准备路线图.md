## 二、你现在就该做的事（1 周内，低投入高回报）

### 🔴 优先级 1：加一个简单的 Critic 自省节点（2-3 小时）

**不要做复杂的交叉验证，先做一个"预算合理性检查"就行。**

```
Travel Agent 推荐餐厅后 → Critic 节点：
  if 推荐人均 > 用户剩余预算 × 0.4:
    标注 "⚠️ 这笔消费占剩余预算 40%+，建议降级"
  if 推荐评分 > 4.5 但 RAG 里有差评记录:
    标注 "⚠️ RAG 反映可能刷评，请核实"
```

这是一个非常小的改动（在 travel_node 的 prompt 或 reply 后加一段校验逻辑就行），但在面试时：

> "我引入了 Critic 自省评估节点，在 Agent 产出推荐后自动做预算冲突检测和 RAG 交叉验证，防止推荐超预算餐厅。"

就这一句话，把 V2.8 → V3.0。

### 🔴 优先级 2：FastAPI + 简单 Web 界面（3-4 小时）

```python
# 最简单的版本
from fastapi import FastAPI

app = FastAPI()


@app.post("/chat")
async def chat(user_input: str, thread_id: str = "default"):
    result = graph.route(user_input, thread_id)
    return {"reply": result}
```

前端用纯 HTML 或 Streamlit 都行。面试官不会在乎 UI 多好看，但会在乎"你有没有把模型部署成可用的服务"。FastAPI 本身就是 Python 后端面试的加分项。

### 🟡 优先级 3：真正的百度地图 MCP Server（可选，2 小时）

你现在 6 个百度工具是 `@tool` 装饰器 + `requests` 直调。如果你想在简历上写"MCP 协议标准化"，就抽 2 小时把它们包成 MCP Server：

```
当前: Agent → @tool 函数 → requests.get(baidu_api)
改为: Agent → MCP Client → MCP Server(百度地图) → requests.get(baidu_api)
```

但说实话，面试官大概率不会深究你是不是真正走 MCP 协议。**这个优先级低于 Critic。**

**🔴 Demo 2：`bind_tools` 底层（必做）**

```python
# demo_bind_tools.py — 看 bind_tools 发给千问的 JSON 长什么样
from langchain_core.tools import tool
from langchain_community.chat_models import ChatTongyi
from langchain_core.messages import HumanMessage
import json

@tool
def search_weather(city: str, date: str = "today") -> str:
    """查询指定城市指定日期的天气"""
    return f"{city} {date}: 晴 28°C"

llm = ChatTongyi(model="qwen-plus").bind_tools([search_weather])
response = llm.invoke([HumanMessage(content="今天中山天气怎么样")])
print(json.dumps({
    "content": response.content,
    "tool_calls": [{"name": t["name"], "args": t["args"]} for t in (response.tool_calls or [])],
    "additional_kwargs": response.additional_kwargs
}, ensure_ascii=False, indent=2))
```

**要看的东西**：函数签名→JSON Schema 转换、`tool_calls` 完整结构、`reasoning_content` 位置。
**面试追问**："如果千问 API 返回的 tool_calls 格式不对，你怎么兜底？"

## 四、面试时最关键的问题（提前准备好答案）

### Q1：「你做的这个 Agent 和直接调 ChatGPT 有什么区别？」

**答**：
> 直接调 ChatGPT 是单次问答，没有工具调用能力，没有记忆，更不知道用户的真实数据。
> 我的 LifeOps 是一个完整的 Agent 系统：
> 1. 它能调用 15+ 个工具获取真实数据（微信账单 CSV、百度地图 API、RAG 知识库）
> 2. 它有 LangGraph 状态机管理多轮对话和工具调用循环
> 3. 它是多 Agent 协作——主 Agent 做决策和融合，子 Agent 做专项执行
> 4. 它有自省机制防止推荐超预算

### Q2：「你遇到最大的技术难点是什么？」

**答**：
> 最大的难点是 LLM 幻觉问题。早期版本 LLM 拿到工具返回的 31 条交易记录后，会在输出时逐条重新生成，导致商户名被修改、金额出现偏差。
> 我的解决方案是确立「搬运工不翻译器」原则——让工具返回预格式化的完整表格，LLM 只做嵌入不做重生成。同时我在 prompt 里加入了明确的禁止规则（禁止说"隐私保护"话术、禁止截断数据）。
> 这个问题的本质是：LLM 适合做语义理解和决策，但不适合精确复制结构化数据。

### Q3：「为什么用 LangGraph 而不是其他框架？」

**答**：
> 我调研过 CrewAI 和 AutoGen。CrewAI 适合线性任务流水线，AutoGen 适合对话式多 Agent。但我的场景需要：
> 1. 主 Agent 持有对话历史，子 Agent 沙箱隔离（防止历史污染，这是 LangGraph 的 StateGraph 天然支持的）
> 2. 主 Agent 能根据子 Agent 返回的空结果自主决定重试或换策略（需要条件边）
> 3. checkpoint 持久化支持多用户会话
> 这三点 LangGraph 最合适。
