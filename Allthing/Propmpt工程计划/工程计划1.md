你的核心痛点非常典型——\*\*Agent 的“自主”不是无引导的“野生自主”，而是“业务规则框架下的结构化自主”\*\*；既不能完全写死链路（僵化），也不能放任 LLM 自由发挥（乱调用/重复调用）。结合你提供的 LifeOps Agent V3.0 设计思路，我给你一套可落地的解决方案，核心是「\*\*分层动态提示词体系 + 业务规则原子化 + 失败策略显式定义\*\*」。



\### 一、先纠正核心认知：Agent 的“自主”是“规则框架下的决策自由”

LLM 本身没有“业务认知”，它的“自主调用”本质是「对 Prompt 中业务规则的理解 + 对工具调用结果的反馈决策」。LifeOps Agent 之所以能处理复杂需求，核心不是“天生懂财务/旅行业务”，而是：

1\. 把业务逻辑拆成「LLM 能理解的原子规则」（比如账单分类规则、RAG 三层降级规则）；

2\. 用「动态 Prompt 拼装」适配不同运行状态（比如数据缺失、工具调用失败）；

3\. 定义「失败后的替代策略」（而不是让 LLM 无意义重复调用）。



你之前的问题：

\- 「写死提示词」→ 链路僵化，是因为 Prompt 是“静态单字符串”，没有结合运行时状态；

\- 「完全自主」→ 乱调用/重复调用，是因为没有给 LLM 明确的「业务边界、成功判定、失败策略」。



\### 二、核心解决方案：设计“分层动态提示词体系”（参考 LifeOps 的动态 Prompt 拼装）

不要写“一个大而全的静态 Prompt”，而是把 Prompt 拆成 4 个分层，运行时根据「业务状态+工具调用结果」动态拼装，既贴合业务，又保留灵活决策空间。



\#### 分层结构（对应 LifeOps 的 `prompt\_templates.py` 设计）

| 分层         | 作用                                                                 | 示例（以账单 Agent 为例）                                                                 |

|--------------|----------------------------------------------------------------------|------------------------------------------------------------------------------------------|

| 基础层       | 定义业务域核心认知（不变）                                           | “你是账单分析 Agent，负责解析微信支付 CSV 账单，交易分类规则：<br>1. 交通类：高铁票/打车/公交；<br>2. 住房类：租房/物业费；<br>3. 餐饮类：餐厅/外卖；<br>4. 其他：非上述类别。” |

| 决策框架层   | 定义工具调用的“决策逻辑”（不变）                                     | “你的决策流程：<br>1. 先判断用户需求是否需要调用工具；<br>2. 调用工具后检查返回结果：<br>   - 非空且格式正确 → 基于结果分析；<br>   - 空/格式错误 → 执行失败策略；<br>3. 同一工具最多调用 2 次，禁止无意义重复。” |

| 运行时状态层 | 根据当前状态动态拼接（核心灵活性）                                   | 状态 1：`data\_status=no\_data` → 追加“当前无账单数据，需提示用户先调用 check\_and\_download\_bill\_email 工具下载账单”；<br>状态 2：`tool\_call\_failed=get\_monthly\_bill\_data` → 追加“get\_monthly\_bill\_data 调用失败，尝试换用 get\_date\_range\_bill\_data 工具，时间范围覆盖目标月份”。 |

| 失败策略层   | 定义“工具返回不符合预期”的替代动作（解决重复调用）                   | “若工具返回空/不符合预期：<br>1. 第一次失败 → 换话术重新调用（比如‘排除交通类’→‘排除交通出行类’）；<br>2. 第二次失败 → 切换兜底工具（比如按月查询→按日期范围查询）；<br>3. 第三次失败 → 放弃调用，告知用户并给出手动解决方案。” |



\#### 代码层面实现（参考 LifeOps 的 prompt assembler）

```python

\# 伪代码：动态 Prompt 拼装函数

def assemble\_prompt(agent\_type, runtime\_state):

&#x20;   # 基础层（固定）

&#x20;   base\_prompt = {

&#x20;       "bill": "你是账单分析 Agent...（核心业务规则）",

&#x20;       "travel": "你是旅行推荐 Agent...（核心业务规则）"

&#x20;   }\[agent\_type]

&#x20;   

&#x20;   # 决策框架层（固定）

&#x20;   decision\_frame = """

&#x20;   你的决策流程：

&#x20;   1. 解析用户需求 → 匹配可用工具；

&#x20;   2. 调用工具后检查结果：

&#x20;      - 成功（非空/格式正确）→ 基于结果响应；

&#x20;      - 失败 → 执行失败策略（最多重试2次，禁止重复调用同一工具）；

&#x20;   3. 禁止编造数据，仅使用工具返回的结构化表格，直接嵌入回复。

&#x20;   """

&#x20;   

&#x20;   # 运行时状态层（动态）

&#x20;   state\_prompt = ""

&#x20;   if runtime\_state.get("data\_status") == "no\_data":

&#x20;       state\_prompt = "\\n⚠️ 当前无可用数据，请先引导用户调用账单下载工具，再进行分析。"

&#x20;   if runtime\_state.get("tool\_failed"):

&#x20;       failed\_tool = runtime\_state\["tool\_failed"]

&#x20;       state\_prompt += f"\\n⚠️ 工具 {failed\_tool} 调用失败，执行替代策略：{get\_alternative\_strategy(failed\_tool)}"

&#x20;   

&#x20;   # 失败策略层（动态）

&#x20;   fail\_strategy = get\_fail\_strategy\_prompt(agent\_type, runtime\_state)

&#x20;   

&#x20;   # 拼接最终 Prompt

&#x20;   final\_prompt = f"{base\_prompt}\\n{decision\_frame}\\n{state\_prompt}\\n{fail\_strategy}"

&#x20;   return final\_prompt



\# 失败策略映射（原子化业务规则）

def get\_fail\_strategy\_prompt(agent\_type, state):

&#x20;   if agent\_type == "bill":

&#x20;       return """

&#x20;       账单工具失败策略：

&#x20;       - get\_monthly\_bill\_data 返回空 → 调用 get\_date\_range\_bill\_data（覆盖该月全范围）；

&#x20;       - get\_date\_range\_bill\_data 返回空 → 调用 get\_data\_inventory 查看本地是否有该时段账单；

&#x20;       - 仍失败 → 告知用户“暂无该时段账单数据，请确认账单已下载”。

&#x20;       """

&#x20;   return ""

```



\### 三、业务深化：把复杂业务拆成“LLM 可执行的原子规则”

你觉得“需求复杂就乱”，本质是业务逻辑没拆透，LLM 无法拆解复杂任务。参考 LifeOps 的设计：

1\. \*\*任务拆解规则原子化\*\*：比如“除去坐车、高铁票、租房后的开销总额”这个复杂需求，LifeOps 主 Agent 会拆成：

&#x20;  - 原子任务1：调用 Bill Agent 获取总支出；

&#x20;  - 原子任务2：调用 Bill Agent 分类统计交通/住房支出；

&#x20;  - 原子任务3：主 Agent 本地计算（总支出 - 交通 - 住房）；

&#x20;  把这个拆解逻辑写进 Prompt 的「决策框架层」，让 LLM 按原子任务执行，而不是直接处理复杂需求。



2\. \*\*工具调用触发规则原子化\*\*：比如 LifeOps 的 RAG 三层降级规则，拆成：

&#x20;  ```

&#x20;  旅行 Agent 工具调用规则：

&#x20;  1. 优先调用 search\_knowledge（本地经验库）；

&#x20;  2. 若返回空/置信度<0.3 → 调用百度地图工具；

&#x20;  3. 若百度地图无结果 → 调用内置联网搜索；

&#x20;  4. 所有工具无结果 → 告知用户“暂无相关信息”。

&#x20;  ```

&#x20;  把这种“if-else”式的原子规则写进 Prompt，LLM 能清晰理解何时该调哪个工具，不会乱调用。



\### 四、解决重复调用：Prompt 中明确“终止条件+替代策略”

LLM 重复调用工具，核心是「不知道什么时候该停 + 不知道失败后该做什么」。参考 LifeOps 主 Agent 面对 Bill Agent 返回空的处理逻辑，在 Prompt 中明确：

1\. \*\*调用终止条件\*\*：“同一工具最多调用 2 次，超过则停止调用，执行替代策略”；

2\. \*\*成功判定标准\*\*：“工具返回非空、包含指定字段（如金额、商户名）、格式为表格 → 判定为成功”；

3\. \*\*替代策略优先级\*\*：“换话术 → 换工具 → 合并已有数据本地计算 → 告知用户失败”。



\#### 反例（易重复调用）：

“你可以调用 get\_monthly\_bill\_data 工具获取账单数据”



\#### 正例（防重复调用）：

“你可调用 get\_monthly\_bill\_data 工具获取YYYYMM的账单数据：

\- 成功判定：返回包含「交易时间、商户名、金额、分类」的表格；

\- 第一次调用返回空 → 换话术（如“202403”→“2024年3月”）重新调用；

\- 第二次调用仍空 → 停止调用，改为调用 get\_data\_inventory 查看本地是否有202403账单；

\- 禁止第三次调用同一工具，禁止编造数据。”



\### 五、落地步骤（从小到大连环验证）

1\. \*\*梳理业务原子规则\*\*：把你的业务拆成「分类规则、工具触发规则、成功/失败判定、替代策略」，写成 LLM 能理解的自然语言（避免技术术语）；

2\. \*\*搭建动态 Prompt 拼装逻辑\*\*：参考上面的伪代码，按“基础层+决策框架层+运行时状态层+失败策略层”拼接，核心是根据运行时状态（比如工具调用结果、数据是否存在）动态追加内容；

3\. \*\*加入可观测性\*\*：参考 LifeOps 的「深度思考追踪+工具调用追踪」，打印 LLM 的 reasoning\_content 和工具调用参数/返回值，定位“乱调用/重复调用”的具体原因（比如 Prompt 规则没写清、LLM 没理解某个业务规则）；

4\. \*\*迭代优化规则\*\*：基于观测数据，细化 Prompt 中的原子规则（比如“交通类”补充“共享单车”、失败策略补充“调用兜底工具X”）；

5\. \*\*加入“自省护栏”\*\*：参考 LifeOps 的 Critic 机制，不修改 LLM 决策，而是监控工具调用次数（比如同一工具调用超2次则强制终止）、返回结果是否符合格式，避免无意义消耗。



\### 总结

Agent 的“灵活调用”不是靠 LLM 天生的“自主”，而是靠「你把业务规则拆透+用动态 Prompt 把规则喂给 LLM+定义清晰的失败策略」。LifeOps Agent V3.0 之所以能处理复杂的财务/旅行需求，核心就是把业务逻辑拆成原子规则，用动态 Prompt 适配状态，用失败策略避免重复调用——这也是你可以复用的核心思路。



简单说：\*\*不要让 LLM “猜业务”，而是让它“按你定义的规则做决策”；不要写死链路，而是写死“决策框架”，让 LLM 在框架内灵活适配状态变化\*\*。
