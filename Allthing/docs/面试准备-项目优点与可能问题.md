## 一、项目核心优点（面试时可主动提及）

### 架构设计

**1. 手写 LangGraph StateGraph 控制流**
- 非 `create_react_agent` 一键封装，自行管理节点、边、条件路由、checkpoint
- 代码位置：[graph/graph_builder.py](../graph/graph_builder.py)、[graph/bill_node.py](../graph/bill_node.py)、[graph/travel_node.py](../graph/travel_node.py)
- ✅ 经得起追问

**2. 子 Agent 沙箱隔离**
- 子 Agent 内部 ReAct 循环的消息历史不污染主 Agent 的 checkpoint
- 主 Agent 传入 query + context，拿回文本结果，中间过程对外部完全透明
- 子 Agent 之间不提供互调工具——所有跨 Agent 数据共享通过 `financial_context` 在 Prompt 装配阶段注入，从物理上消除递归调用风险
- 代码位置：[bill_node.py](../graph/bill_node.py) 的 `run_bill_agent()` 沙箱入口、[cross_agent.py](../graph/cross_agent.py) 的 `financial_context` 提取
- ✅ 经得起追问

**3. MCP 协议 + 原生 @tool 双通道容灾**
- 百度地图优先通过 MCP Server（进程级解耦）调用，失败时自动 fallback 到原生 `@tool` 函数
- 全部 6 个地图工具（POI搜索/详情/路线/天气/地理编码/周边搜索）覆盖完整
- 代码位置：[travel_node.py:32-63](../graph/travel_node.py#L32-L63) 的 `_build_travel_tools()`
- ✅ 经得起追问

### 防幻觉 / 数据可靠性

**4. "搬运工不是翻译器"原则**
- 工具返回预格式化的完整表格（含 `__stats__` 预聚合统计），LLM 只嵌入不翻译
- Prompt 明确禁止"隐私保护话术""其余XX笔省略""编造交易记录"

### 核心经验（面试时最能体现深度的部分）

**15. 从"细粒度工具失控"到"预计算+LLM只做语义包装"**
- 最初拆了 7+ 个原子化工具（读数据/算统计/画图/展示...），导致 LLM 无限循环、幻觉、token 爆炸
- 根因分析：LLM 不擅长在细粒度工具中自行探索正确的调用链路，搜索空间 O(N!)
- 解决方案：后端预计算所有统计量 → 一次返回 → LLM 用自然语言说出来，决策空间从 O(N!) 压缩到 O(1)
- ❗ 这是整个项目最有价值的经验教训

**16. 工具数量克制**
- 当前只保留必要的账单工具（1 个灵活读数据 + 1 个数据盘存）和地图工具（MCP 6 个 + RAG 1 个）
- 原则：确定性代码做计算，LLM 只做语义包装和自然语言生成

**17. 统一主 Agent 提示词 + 逐步推进模式（V3）**
- 去掉了旧版的"路由/合成两阶段分离"设计——不再有 `ROUTING_PROMPT_V2` 和 `SYNTHESIS_PROMPT_V2` 两套独立 Prompt
- 合并为一份 `MAIN_AGENT_PROMPT_V3`：四种场景（纯闲聊/账单/出行/综合）对号入座，每轮全工具可用，LLM 自己判断"继续行动"还是"回复用户"
- 核心思想："每次只调一个工具，看到结果再决定下一步"——用 Prompt 约束行为而非代码分叉，比硬编码 `has_tool_results` 分叉更灵活
- 代码位置：[task_decomposer.py](../routing/task_decomposer.py) 的 `MAIN_AGENT_PROMPT_V3`、[graph_builder.py](../graph/graph_builder.py) 的统一 ReAct 循环
- ✅ 经得起追问

## 三、面试官可能问的问题 & 回答思路

### 架构类

**Q1: 为什么用 LangGraph 而不是 CrewAI / AutoGen / Dify？**

回答思路：
- LangGraph 给你的是图状态机的控制力——节点、边、条件路由、checkpoint 全部自己控制
- CrewAI/AutoGen 是高层封装，把 Agent 协作模式固化了（顺序/层级/辩论），灵活性不够
- LangGraph 的 StateGraph 让你可以精确控制每一步的数据流向——这正是 Agent 开发中最需要控制的地方
- 实际例子：我的主 Agent 图 = `main_agent ⇄ tools` 统一 ReAct 循环，每轮全工具可用，LLM 自己判断继续还是结束。封装框架做不到这种"我可以自己决定图里有几个节点、边怎么连"的粒度

**Q2: LangGraph 的 StateGraph 和 LangChain 的 AgentExecutor 有什么区别？**

回答思路：
- AgentExecutor 是一个黑盒 while 循环（LLM→工具→LLM→工具→...），你只能配置，不能干预循环中间的过程
- StateGraph 让你定义图结构——有几个节点、节点间怎么流转、每个节点的输入输出是什么、什么时候结束
- 比如你的项目：主 Agent 图 = `main_agent ⇄ tools`，子 Agent 图 = 同样的模式但独立隔离，两个图彼此不污染
- 如果需求是"LLM 调 3 轮工具后，插入一个代码层的质量检查，不通过就回到第一步"——StateGraph 天然支持，AgentExecutor 做不到

**Q3: 为什么子 Agent 要做沙箱隔离？不隔离会怎样？**

回答思路：
- 子 Agent 内部有 6-8 轮自己的 ReAct 循环（LLM→工具→LLM→工具→...），每轮产生 SystemMessage、AIMessage、ToolMessage
- 如果这些消息全部写入主 Agent 的 messages 列表 → checkpoint 爆炸 + 主 Agent 被子 Agent 的内部推理噪音干扰
- 你的方案：子 Agent 作为工具被调用 → 传入 query → 内部独立 ReAct → 只返回最终文本给主 Agent
- 主 Agent 看到的是一条干净的 ToolMessage（内容=子Agent的最终回复），不是十几条中间的推理碎片

**Q4: SqliteSaver checkpoint 多用户隔离怎么做的？**

回答思路：
- SqliteSaver 是 LangGraph 的 checkpoint 持久化方案，用 SQLite 存储对话状态
- 隔离方式：`config = {"configurable": {"thread_id": user_id}}`
- 每个 thread_id 对应一个独立的对话线程，消息历史不互通
- 代码位置：[graph_builder.py:376-378]

**Q5: 跨 Agent 之间怎么共享数据？怎么防止互相调用导致的递归？**

回答思路：
- 早期版本 Bill Agent 和 Travel Agent 确实有互相调用的工具（`query_bill_budget` / `query_travel_savings`），需要 `allow_cross_agent=False` 参数来控制沙箱工具列表防止递归
- 但实践中发现两个问题：① 控制逻辑绕，维护成本高；② 更重要的是——子 Agent 自己做跨 Agent 决策质量不如主 Agent
- 所以 V3 中完全删除了子 Agent 互调工具。所有跨 Agent 数据共享改为在 Prompt 装配层完成：
  - `cross_agent.py` 的 `financial_context` 提取逻辑从上游结果中抽取出 `daily_baseline`、预算状态等关键数值
  - `assembler.py` 在装配下游 Agent 的 System Prompt 时注入这些数据
  - 子 Agent 拿到的是"我已经帮你算好的数字"，只需要在自己的领域内使用它，不需要自己调另一个 Agent
- 这样做的好处：① 从物理上消除递归——工具列表里根本没有跨 Agent 工具；② 决策权回归主 Agent——跨 Agent 协调由主 Agent 在顶层完成，子 Agent 专注自己的领域
- 代价：灵活性降低——子 Agent 不能在执行中主动问另一个 Agent"你能帮我查一下XX吗"。但目前的场景不需要这个灵活性

### 防幻觉类

**Q6: "搬运工不是翻译器"具体怎么实现的？**

回答思路：
- 问题起源：早期版本 LLM 拿到 31 条交易记录后逐条重生成 → 商户名被改、金额编造、出现"其余XX笔省略"
- 解决方案：
  1. 工具层用 pandas 预计算统计量（`__stats__`：总支出/总收入/日均/记录数），不依赖 LLM 算
  2. 超过 100 条记录不返回明细（硬控），防止 LLM 面对大量结构化数据时逐条重生成
  3. Prompt 明确：禁止"隐私话术""省略话术""编造交易记录"
  4. OutputCritic 后置检测：回复中出现禁止话术 → 打日志告警
- 核心认知：LLM 适合语义理解和决策，不适合精确复制结构化数据

**Q7: 怎么处理 LLM 编造金额/日期？**

回答思路：
- 两层防护：
  1. **前置**：正则数字对照表（task_decomposer.py:80-83），用户输入中的所有阿拉伯数字都被提取为对照表，LLM 提取的金额必须在表中找得到
  2. **后置**：DATA PANEL（bill_node.py:194-237），工具返回的数据用 `【DATA PANEL — 以下数字由 Python 精确计算】` 格式包装，规则明确："回复中涉及的任何数字必须来自 DATA PANEL，不得编造"
- 这不能 100% 防止，但已经把概率降到很低

**Q8: 你的 Critic 审查是正则匹配，正则怎么拦得住 LLM 的变化？**

如实回答：
- 当前确实是正则匹配，覆盖已知的禁止话术模式
- LLM 换个说法就能绕过（比如不说"篇幅原因"而说"因字数限制"）
- 但正则的优势是：零 token 消耗、零延迟、100% 确定性
- 正则适合做第一道防线（拦截已知坏模式），复杂的语义审查应该用 LLM Critic（下一步改进方向）
- 完全靠正则不行，但完全没有正则也不行——两者互补

### 性能 & 成本类

**Q9: Token 消耗怎么控制的？**

回答思路：
- ① 动态 Prompt 拼装：平时只加载 base + decision 两层，出问题才激活降级/失败策略层
- ② 消息历史截断：只保留最近 10 条
- ③ 工具返回硬控：超过 100 条记录不返回明细，只返回统计
- ④ 预计算统计量：pandas 在工具层算好，不需要 LLM 自己遍历原始数据计算
- ⑤ V3 逐步推进模式：Prompt 约束"每次只调一个工具"，避免一次性并行调多个工具后产生大量无效工具返回堆积在上下文

**Q10: 如果有 100 万条账单数据，性能扛得住吗？**

回答思路：
- 当前按月分片存储（data/bills/YYYYMM.csv），查询时只读涉及月份的 CSV
- 但全表扫描式的查询（查整年）确实会有性能问题
- 优化方向：① 预聚合月度统计缓存 ② 引入 DuckDB/ClickHouse 做列式存储 ③ 对常用查询做物化视图
- 当前项目规模（个人用户，每月几百条记录）不需要这些，但架构上预留了扩展空间

**Q11: 消息历史无限膨胀怎么解决的？**

回答思路：
- 全局截断：`if len(messages) > 10: messages = messages[-10:]`
- 但这不是最优方案——截断可能丢掉关键上下文
- 更好的方案是分层压缩（下一步）：工具返回 > N 字符只保留结构化摘要；早期轮次做压缩保留 "做了什么+关键数字"
- 代码位置：[graph_builder.py:207-209](../graph/graph_builder.py#L207-L209)

### 工程实践类

**Q12: MCP 协议和原生 @tool 怎么选？什么时候用哪个？**

回答思路：
- MCP 优势：标准协议，进程级解耦，工具提供方和消费方独立开发部署。百度地图 MCP Server 是第三方提供的，一行代码不写就能用 6 个地图工具
- @tool 优势：零网络开销，调试方便，适合自己维护的工具
- 你的策略：地图用 MCP 优先（因为地图服务逻辑复杂、第三方已提供成熟 Server），失败时自动 fallback 到 @tool
- 自己的业务工具（账单解析、RAG、省钱管理）用 @tool，因为逻辑简单、需要灵活调整

**Q13: 百度地图 MCP Server 挂了怎么办？**

回答思路：
- `_build_travel_tools()` 检测到 MCP 不可用 → 自动切换为原生 `@tool` 函数（直接调百度 HTTP API）
- 对 LLM 来说完全透明——它只看到 N 个地图工具，不知道背后是 MCP 还是原生
- 代码位置：[travel_node.py:40-62](../graph/travel_node.py#L40-L62)

**Q14: WebSocket 流式输出具体怎么实现的？地图数据为什么要分离传输？**

回答思路：
- Agent 的非流式 invoke 是阻塞的，用户需要等整个 ReAct 循环跑完才能看到回复 → 体验差
- 流式输出：Agent 生成一个字就推一个字到 WebSocket，前端逐字渲染
- 地图数据分离原因：地图数据是结构化的 JSON（路线坐标点、POI 列表），不适合嵌在 Markdown 文本里
- 方案：Travel Agent 运行完后 `_extract_map_data()` 提取地图 JSON → 存入全局变量 `_last_travel_map_data` → server.py 通过 WebSocket 单独推给前端 BMapGL 渲染
- 代码位置：[travel_node.py:91-96](../graph/travel_node.py#L91-L96)、[travel_node.py:242-433](../graph/travel_node.py#L242-L433)

### 开源 & 技术选型类

**Q15: 为什么用 ChromaDB 而不是 FAISS / Milvus / Pinecone？**

回答思路：
- 项目规模：个人知识库，不到 100 篇 Markdown 文档，几百条记录
- ChromaDB：零配置、Python 原生、PersistentClient 本地磁盘持久化、单文件部署
- FAISS：性能强但需要自己管理持久化
- Milvus：太重，需要 Docker，对于个人项目是过度设计
- Pinecone：需要网络，有成本
- 选型原则：够用就好，不为技术而技术

**Q16: 为什么用 qwen 而不是 GPT-4 / Claude？**

回答思路：
- qwen-max 在中文场景（账单分析、美食推荐）表现好，价格低
- `enable_thinking=True` 能看到推理过程，对调试 Agent 行为非常重要
- 国内部署不需要翻墙
- 但如果做更复杂的多步推理，Claude/GPT-4 的指令遵循能力更强——这是模型选择上的 trade-off

### 反思类（最重要）

**Q17: 遇到最头疼的技术问题是什么？怎么解决的？**

回答思路（按时间线讲）：
1. **细粒度工具导致无限循环**：LLM 面对 7 个账单工具不知道怎么组合 → 反复调、幻觉、token 爆炸
   - 解决：合并工具、后端预计算、LLM 只做语义包装
2. **LLM 编造交易数据**：31 条记录逐条重生成 → 商户名错、金额编造
   - 解决："搬运工不是翻译器"原则 + DATA PANEL + OutputCritic
3. **tool_call_id 断裂导致 API 报错**：DeepSeek 兼容格式要求每个 tool_call 必须有对应 ToolMessage
   - 解决：`_sanitize_messages_for_api` 检测并清理不完整的 tool_calls

**Q18: 做完这个项目，你对 Agent 开发的认识有什么变化？**

回答思路：
- 最大的认知变化：**不是越"智能"越好，是越"可控"越好**
- 一开始追求 LLM 自主决策一切——细粒度工具、灵活链式调用
- 后来发现 LLM 在开放空间中的决策质量远不如确定性代码
- 现在的方法论：**确定性代码做计算和数据流转，LLM 只做它最擅长的事——语义理解和自然语言生成**
- 好的 Agent 不是让 LLM 替代整个系统，而是让 LLM 做系统外面的那层自然语言皮

## 四、项目可升级方向（优先级排序）

### P0：核心循环修复（改动小、效果大）

**1. ~~打通主 Agent ReAct 循环~~ ✅ 已完成**
- 旧问题：`has_tool_results` 分叉导致合成阶段丢失 sub-agent 工具
- 已实现：删除两阶段分叉，统一为一套全工具 ReAct 循环；`MAIN_AGENT_PROMPT_V3` 四种场景对号入座，"每次只调一个工具，看到结果再决定下一步"
- 同时删除了 `ROUTING_PROMPT_V2` / `SYNTHESIS_PROMPT_V2` 两套 Prompt 和 calculation 计算模块

**2. 加入轻量 Evaluator 节点**
- 每次工具返回后，确定性代码检查结果质量：
  - `"暂无数据" in result` → 自动提示 LLM 换参数重试
  - `len(result) < 阈值` → 标记为可疑
  - `"error" in result` → 触发降级策略
- 零 token 消耗，确定性判断
- 改动范围：在 `main_agent ⇄ tools` 循环中插入一个 evaluator 函数
- 注意：V3 Prompt 的"逐步推进"已用软约束解决了部分问题，但代码级的 Evaluator 比 Prompt 约束更可靠

### P1：护栏升级

**3. 关键场景引入 LLM Critic**
- 在 Generator 产出回复后，用另一个 LLM 从不同视角审查：
  - 数字是否都能在工具返回中找到？
  - 逻辑是否自洽？（如"预算 30 元"但推荐了人均 80 的店）
  - 是否遗漏了用户的关键需求？
- 不通过 → 退回修改（附具体意见），最多 2 次
- 只在高风险场景（涉及金额、推荐）启用，其他场景跳过

**4. 上下文智能压缩**
- 工具返回 > 2000 字符 → 保留结构化摘要
- 超过 N 轮历史 → 早期轮次压缩为"做了什么+关键数字"
- 工具调用链折叠：合成阶段不需要知道"数据怎么来的"，只需要"数据是什么"

### P2：功能增强

**5. 长期记忆 / 用户偏好学习**
- 每次对话结束后异步提取用户偏好（"不吃辣"、"预算敏感"、"住在东区"）
- 存入轻量用户 profile（JSON 或 SQLite）
- 下次对话自动注入到 System Prompt
- 用户纠正 Agent 的错误推荐 → 记录原因 → 下次自动过滤

**6. 流式 reasoning_content 推送**
- 当前深度思考日志（`enable_thinking`）只输出到控制台
- 推到前端可以让用户看到 Agent "在想什么"
- 实现：WebSocket 单独推送 `reasoning_content` 块

**7. 系统化 Agent 行为测试**
- 参考 `/rag_test` 的模式，扩展为 Agent 行为评估：
  - 给定输入 → 期望输出（或期望调用了某个工具）
  - 批量跑 → 计算准确率
- 每次改 Prompt 后跑一次回归测试

### P3：体验优化

**8. 预算预警定时推送**
- 定时任务：每周/每月检查预算状态
- 超预算 → 通过 WebSocket 推送预警（"本月餐饮已超预算 15%，建议控制"）

**9. 多城市知识库扩展**
- 当前知识库以中山为主
- 扩展到其他城市只需添加 Markdown 文件 → 导入 ChromaDB

**10. 前端对话流优化**
- 支持对话分支（用户对某个推荐不满意 → 在同一条对话中回溯到分叉点）
- 推荐结果可视化（每个推荐附卡片：图片/评分/价格/距离）

## 五、面试时的叙事建议

### 不要这么说

> "我做了一个基于 LangGraph 的多 Agent 智能生活管家，具备自适应循环、Agentic RAG、Critic 自省护栏..."

→ 面试官会追问你每一个虚词，然后发现实际深度不够，给你扣分。

### 建议这么说

> "我做了一个基于 LangGraph 的个人生活管家项目，核心是用 Agent 的方式把微信账单分析和百度地图出行推荐串起来。
>
> 这个项目让我最大的收获不是技术上用了什么框架，而是**对 Agent 开发的认识有了一个反转**——
>
> 我一开始把工具拆得很细，账单这边分了读数据、算统计、画图表、展示表格好几个工具，觉得这样 Agent 灵活。但上线后发现 LLM 面对一堆工具不知道怎么组合，反复调、幻觉、token 爆炸。
>
> 后来我把策略反过来了——确定性代码预计算所有统计量，一次返回给 LLM，LLM 只负责用自然语言把数字说出来。工具少了，准确率反而上去了，token 消耗还降了一大截。
>
> 这个经历让我意识到：好的 Agent 不是让 LLM 替代整个业务系统，而是让 LLM 做系统外面的那层自然语言皮。确定性代码做计算，LLM 做语义理解——各司其职才是最优解。"

### 如果被追问"那你觉得 Agent 的能力边界在哪？"

> "我认为当前 LLM 级别的 Agent，最可靠的模式是：确定性代码负责数据管线、计算、校验这一整条'硬逻辑'链；LLM 负责理解用户意图、决策调用哪个工具、以及把工具返回的数据用自然语言包装输出。
>
> LLM 不适合做精确计算、不适合处理大量结构化数据的逐条翻译、不适合在没有约束的开放空间里自行探索正确的工具调用链路。
>
> 什么时候 LLM 的推理能力提升到可以可靠地在 O(N!) 的工具组合空间中不走丢，这个边界才能再往外推。但目前这个阶段，越克制越可靠。"
