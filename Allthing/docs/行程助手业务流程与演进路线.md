#### 能力2: 财务模块集成（解决"盲目推荐"问题）

**解决的问题**: 不知道用户还剩多少钱，可能推荐超出承受能力的店铺。

**三种数据来源（由简到繁）**:

##### 方式1: 手动配置（V2.0初期用这个）⭐推荐
```json
// config/budget.json
{
  "food_budget": {
    "total": 2000,
    "spent": 1200,
    "remaining": 800,
    "days_left": 10,
    "daily_avg": 80
  },
  "preferences": {
    "save_mode": false,
    "priority": "balance" // taste / price / balance
  }
}
```

**优点**: 最简单，零开发成本  
**缺点**: 不够精确（无法追踪真实消费）

##### 方式2: CSV导入（V2.0中期加入）
```
用户操作流程:
  1. 微信 → 我 → 服务 → 钱包 → 账单
  2. 点击右上角"..." → 导出账单
  3. 选择月份 → 确认 → 得到CSV文件
  4. 上传到系统或放入 data/history/ 目录

系统自动处理:
  - 解析CSV（日期/金额/商户名/类别）
  - 关键词分类:
    * 包含"美团/饿了么/外卖" → 餐饮
    * 包含"滴滴/打车/公交" → 交通
    * 包含"电影/KTV/游戏" → 娱乐
  - 更新 budget_current.json
  - 生成统计图表（matplotlib）

频率建议: 每周或每月导入一次（每次5分钟）
```

**财务规则引擎（核心逻辑）**:
```yaml
规则1: 价格过滤
  触发条件: 搜索结果返回后
  逻辑: 
    if 店铺人均 > 日均预算 × 1.5:
      标注 "⚠️ 略超预算"
    if 店铺人均 > 剩余预算 × 0.3:
      标注 "❌ 超支风险"
      
规则2: 时间感知
  触发条件: 每次推荐前检查日期
  逻辑:
    if 当月天数 >= 25:
      触发 "月底省钱模式"
      → 降低价格权重 × 0.7
      → 提升性价比权重 × 1.3
      → 在回复中提醒预算紧张
      
    if 是周五/周六/周日:
      触发 "周末溢价模式"
      → 提醒排队风险
      → 建议提前取号
      
规则3: 异常检测
  触发条件: 后台定时任务（每日18:00）
  逻辑:
    if 今日消费 > 历史日均 × 2:
      推送预警通知
      "今日已消费¥XXX（日均¥XX），如非必要晚餐控制在¥XX以内"
```

### 技术类问题

**Q1: 为什么选择LangChain而不是自己写一个Agent框架？**
```
A: LangChain是目前最成熟的LLM应用开发框架，
   它提供了：
   1. 标准化的Tool抽象（@tool装饰器）
   2. 成熟的Agent循环（ReAct模式）
   3. 丰富的集成（100+工具/LLM/向量库）
   4. 活跃的社区支持（GitHub 80k+ stars）
   
   如果我自己写，需要重新实现这些基础设施，
   而且难以跟上LLM领域的快速迭代。
   
   但我也研究了它的源码，理解其底层原理，
   不是单纯的"调包侠"。
```

**Q2: Function Calling的原理是什么？**
```
A: Function Calling是大模型的一种特殊能力，
   让LLM能够输出结构化的函数调用参数，
   而不是自然语言文本。
   
   工作流程：
   1. 用户输入问题
   2. LLM分析意图，决定是否需要调用工具
   3. 如果需要，输出JSON格式的函数名+参数
   4. 系统执行函数，获取结果
   5. 将结果传回LLM，让它生成最终回答
   
   在我的项目中，
   定义了6个工具（@tool装饰器），
   Agent会根据用户问题自动选择最合适的工具调用。
```

**Q3: RAG解决了什么问题？为什么需要它？**
```
A: RAG解决的是LLM的两个核心问题：
   
   1. **知识滞后性**: LLM的训练数据有截止日期，
      无法知道最新发生的事情（如新开的餐厅）
      
   2. **幻觉问题**: LLM可能编造不存在的信息，
      特别是具体的事实性数据
      
   在我的项目中，RAG的作用是：
   - 存储百度API无法提供的"人类经验"
     （如排队时长、真实口感、避坑警告）
   - 通过语义检索快速找到相关经验
   - 让Agent的回答更有"人情味"和实用价值
   
   这比单纯调API更有差异化竞争力。
```

**Q4: 如何保证知识库数据的质量？**
```
A: 我采用了三层质量保障机制：
   
   1. **源头控制**: 只收录经过验证的真实经验
      （自己实测或可信用户反馈）
      
   2. **时效性衰减**: 每条数据带时间戳，
      超过6个月未更新的自动降权
      
   3. **冲突检测**: 如果API数据和RAG数据矛盾
      （如API说4.8分但RAG说刷评），
      会同时展示两方数据让用户自己判断
```

   4. **经验传承**: 社区的智慧可以共享

   - 个人日常决策（吃什么/去哪玩）

### 项目管理类问题

**Q7: 你遇到的最大技术难点是什么？怎么解决的？**
```
A: 最大的难点是**平衡实时性和准确性**。
   
   具体表现：
   - 百度API返回的评分可能不准（刷评问题）
   - 本地知识库的经验可能过时（店铺倒闭/换老板）
   - 用户的需求很模糊（"推荐好的"——什么是好？）
   
   我的解决方案：
   
   1. **多源验证**: 当关键决策时（推荐高价店），
      同时查百度和高德，对比评分差异
      
   2. **置信度标注**: 对每条数据标注可靠程度，
      低置信度的明确告诉用户"此信息可能过时"
      
   3. **引导式澄清**: 当需求模糊时，
      反问用户"更看重口味还是性价比？"
      而不是瞎猜
      
   4. **持续迭代**: 设计了反馈机制，
      用户可以说"这个推荐不好"，
      系统会记录下来改进后续推荐
```
